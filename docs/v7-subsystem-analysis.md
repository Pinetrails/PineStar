**How it works**

- COORDINATE SYSTEMS: three layers. (1) Tile grid: COLS=78 x ROWS=55, TILE=12px (map.js:8). (2) World pixels: tileX*12; map.js exposes W=COLS*TILE=936, H=ROWS*TILE+14=674 (the +14 leaves room for the extruded south hull face). (3) Screen: the canvas is a single fixed-resolution buffer (cv.width=W, cv.height=H in render.js:882) CSS-stretched to fit; render.js:876 toLocal() converts mouse events back via (clientX-rect.left)*(W/rect.width). A body stores px/py in world pixels AND tile{x,y}; foot anchor convention is px = tileX*T + T/2, py = tileY*T + T-1 (agents.js:67,630).
- THERE IS NO SCROLLING CAMERA. The whole station fits in one 936x674 buffer and is scaled by CSS (index.html canvas#station). 'Camera' = the CSS scale of that fixed buffer. Panning/zoom would have to be added (drawImage offset or ctx.translate/scale) — none exists today.
- PER-FRAME RENDER LOOP (render.js:787 frame(tMs), called from main.js:102 inside requestAnimationFrame after SIM.tick + WORLD.tick): (a) fill space black + draw 230 scrolling parallax stars; (b) lazily buildBase() once, then ctx.drawImage(baseCv) — the entire static environment is a prebaked offscreen canvas; (c) drawExteriorAnim() for blinking dish/nav LEDs/engine glow; (d) build a y-sort list of {y, draw} for all furniture, parcels, and agent bodies, sort ascending by y, draw in order (render.js:806-839) — this is the painter's-algorithm depth sort; (e) ctx.drawImage(lightCv) over everything (baked darkness with light carved out); (f) drawGlows/drawLabels/drawHazards/drawPropHover and floating +$ text and hover name tags.
- BAKING (render.js:107 buildBase): all static geometry is rendered ONCE into baseCv (an offscreen canvas the size of the world): hull plate + seams + rivets, per-room and per-corridor procedural floors (bakeRoomFloor/bakeCorridorFloor), edge ambient occlusion, door thresholds, walls (bakeWalls draws n-faces tall and s/w/e as wall-tops to sell the tilt), additive room lighting pools, rounded-corner (chamfer) arc walls, and a downward hull extrusion (bakeHullExtrusion stamps the silhouette down to fake 3D side walls). Re-baked only if baseCv is null. THIS IS WHY USER-PLACED OBJECTS ARE HARD TODAY (see simulatedParts).
- LIGHTMAP (render.js:280 buildLightMap -> lightCv): a full-screen dark overlay (rgba(10,8,4,0.62)) painted over rooms/corridors, then light is CARVED BACK with globalCompositeOperation='destination-out' radial gradients at room centers, lamp positions (lampPos[]), doorways, and windows, plus a source-over vignette. Drawn over the WHOLE scene each frame so agents/furniture sit in the same light. A few lamps (flickers[]) get a live additive shimmer in drawGlows().
- TILE/ROOM/ZONE MODEL (map.js): zones{} maps a zoneId to an inclusive tile rect {x1,y1,x2,y2}. ROOM_IDS lists the 10 real rooms; everything else (hub, spines, corridors) is a corridor. zoneGrid[idx(x,y)] = zoneId per tile; blocked[] = Uint8Array of impassable tiles; sitTiles{} = 'x,y'->true for seats. allRects[] drives all bake loops. roomAt(tx,ty) returns roomId or 'corridor'. A 'room' is therefore just a labeled rectangle of tiles plus baked decoration — there is no Room object/class.
- WALKABILITY + PATHFINDING (map.js): walkable(x,y) = in-bounds AND zoneGrid!=null AND !blocked. canStep enforces zone boundaries except through doorSet (built from doorDefs pairs). path(sx,sy,tx,ty) is a plain BFS over 4-neighbors returning an array of {x,y} tiles (map.js:358). propAt(tx,ty) and pwGrid give tile->interactive-furniture lookup for hover/click (also checks one tile south for sprite overhang).
- AGENT BODY + WALK/SIT/WORK STATE MACHINE (agents.js WORLD): bodies{id} each have px,py,tile,path[],state('work'|'walk'|'idle'|'social'),sitting,working,dir,phase,plan. tick(dt,t) (agents.js:616): if path non-empty, move px/py toward path[0] at 42*pace px/s, set dir from dominant axis, snap tile on arrival, shift path, call arrive() when empty. goTo(b,tx,ty) computes a BFS path and sets state='walk',sitting=false. arrive() sets posture by goal: at the home station tile it sets state='work',sitting=true,dir='north' (desks face away from camera). working = (state==='work' && hasTask) is set in think() (agents.js:471). So the entire 'walk to your computer, sit, work' loop ALREADY EXISTS — goTo a station tile, arrive sits you, a task flips working=true.

**Risks**

- Runtime object placement fights the bake-once design: the entire environment (floors/walls/hull/lighting) is precomputed into baseCv/lightCv and only built when null. Any placed/moved object needs zoneGrid/blocked/sitTiles/pwGrid updates AND a re-bake (or a new dynamic layer). Re-baking the whole 936x674 canvas per placement is acceptable (it's not per-frame) but must be wired deliberately — there is no invalidate/rebuild API today.
- No camera/scroll/zoom: a user-built room larger than the fixed buffer will not fit. Adding a camera touches both rendering (transform before world layers) and input (toLocal must invert the transform) — easy to get half-done and break hit-testing.
- Coordinate coupling: agents anchor at py = tileY*T + T-1 and the lightmap/extrusion assume the fixed layout (e.g. H gets +14 for the south hull). Changing TILE size or world bounds ripples through bake math, AO depths, wall heights, and shadow offsets.
- Walkability vs furniture footprint: blocked/sitTiles/pwGrid are built once at module load from the literal furniture[]. Placing an object without updating all three desyncs collision, seating, and click-targeting (e.g. agents walking through a new object, or no sit tile registered).
- 'working' is cosmetic and tied to SIM.taskId; if SIM is removed without re-pointing b.working/f.work, all seated-at-computer screen animation goes dark even when a real agent is running.
- sprites.js is huge (3674 lines) and entirely station-themed; reusing it wholesale imports a lot of bespoke art. Cherry-pick the helpers + the few object types you need (desk/pixelrig/agent) rather than dragging in the full economy-specific catalog.
- PixelLab sprite path assumes a static manifest.json fetched at init; per-user runtime avatar generation needs an async pipeline (generate -> load -> tint) and a graceful procedural fallback while frames are missing (the drawAgent SPRITES.ready check already provides this pattern).

## Simulation & Economy Core (v7 "StarNet")

**Purpose.** The deterministic-ish game engine that drives the colony: a per-game-minute "heartbeat" advances a single global state object S, spawns tasks for 17 agents, walks each task through a research -> production -> publishing -> sales pipeline, and books revenue/cost into an economy. Every agent "doing work," every deliverable's quality, every token cost, and every sale is invented locally with Math.random() and content pools — there are no model calls, no tool calls, and no money. This is the exact subsystem that must be replaced (or wrapped) so that real model invocations, real tool calls, and real metered cost stand in for the faked numbers.

**Key files**

- `C:\Users\andro\OneDrive\Desktop\v7\js\sim.js` — The simulation engine: global state S (newState), minute heartbeat (minuteTick), task pipeline (generators -> completeTask -> finalize -> heraldHandoff -> salesTick), fake quality (rollQuality), fake per-task cost (taskCost), fake revenue (earn/salesTick), feedback-driven stat growth (feedback), Ultron intent routing (playerMessage), and serialize/load.
- `C:\Users\andro\OneDrive\Desktop\v7\js\data.js` — Static config + the fake economy constants: DATA.MODELS cost ranges and DATA.DAILY_SUBS (the per-model token-cost model), DATA.KINDS revenue ranges, DATA.AGENTS roster (model/harness assignment), DATA.ROOMS, DATA.STAGE_COUNTS, and every content pool (DATA.C.*) that supplies the faked deliverable text.
- `C:\Users\andro\OneDrive\Desktop\v7\js\main.js` — The heartbeat driver and persistence: requestAnimationFrame loop() converting real time*speed into SIM.tick(mins); save/load/reset to localStorage 'starnet_save_v1'; 30s + beforeunload autosave; boot sequence.

**How it works**

- HEARTBEAT: main.js loop() (line 94) runs on requestAnimationFrame. It accumulates real wall-time into simAcc at settings.speed, and every time 1000ms of sim-time elapse it calls SIM.tick(mins) (capped at 30 mins/frame). SIM.tick (sim.js:814) just loops minuteTick() N times. So one game-minute == one logical sim step; default 1 game-min per real second.
- GLOBAL STATE S: created by newState() (sim.js:9-38). Single mutable object holding: time (minutes since day1 07:00), mode (MANUAL/AUTO), party timer, rev {total,etsy,fiverr,other}, costs, station level/xp, agents map, tasks[], feedback[], notifs/ops/chat logs, listings counts, insights counts (research inventory), saasProjects[], mrr, pivots map, fiverrRating, history[], dayAcc accumulators, kindStats telemetry, shipQueue[]. Per-agent record (sim.js:12): skill, morale, autonomy, reliability, xp, level, tasksDone, earned, spent, fbApproved/Denied, taskId, statusTxt.
- MINUTE TICK (sim.js:681): S.time++, then for each agent: if idle, pull the next 'todo' task for that agent and mark it 'active'; if working, advance t.prog by a computed speed and call completeTask when prog>=dur. Then morale drifts toward 62. Then generators() spawns new work, salesTick() rolls sales, the shipQueue fallback flushes overdue publishes, the ultronQueue flushes delayed chat lines, AUTO-mode autopilot resolves stale feedback, and on minute boundaries pivotCheck/checkMilestones (every 60) and dayRollover (every 1440) fire.
- TASK SPAWN: generators() (sim.js:412) is the pipeline source. Each agent has a genReady(id, cooldown) gate (sim.js:401) that fires on a randomized cooldown, plus agentFree() (sim.js:406). NOVA/CURIE emit 'research' tasks that increment S.insights[store]. Factory agents (FORGE/VECTOR/PROMETHEUS) consume an insight (S.insights[store]--) to emit apparel/candle/custom tasks. PIXEL/ATLAS/QUILL/CIPHER/VYBES emit fiverr/assets/article/saas/song tasks on their own cadence. So 'research -> production' is literally an integer inventory counter (insights) being incremented by researchers and decremented by factories.
- TASK PROGRESS (the FAKE WORK timer): minuteTick line 695 computes sp = speedMult() * (0.7 + skill/180) * (morale<40?0.75:1) * (partyOn?0.5:1) and does t.prog += sp until t.prog >= t.dur. dur is a random integer (e.g. U.irnd(40,70)) set at task creation. This loop IS the 'agent working on the computer' — purely a counter racing a random target, no work performed.
- COMPLETION & QUALITY (FAKE QUALITY): completeTask (sim.js:174) books cost via taskCost(), then invents quality via rollQuality() (sim.js:160): q = 32 + skill*0.55 + (morale-60)*0.18 + U.rnd(-13,13) + perkBonus, with retry/note/rush/low-morale modifiers, clamped 15-99. If quality < flagBelow(agent) for FLAGGABLE kinds (or a commander flag is set), the task goes to 'review' and a fake self-doubt feedback entry is created; otherwise finalize() runs.
- FINALIZE & PIPELINE BRANCH (sim.js:212): bumps agent xp/level/skill, station xp, kindStats. Then a switch on t.kind: 'research' increments S.insights (feeds production); production kinds (apparel/candle/custom/assets/song/article) push a 'ship' onto S.shipQueue to be hand-carried to HERALD; 'publish' increments S.listings (feeds sales) and kindStats.shipped; 'fiverr' books revenue immediately via earn(); 'saas' advances a 3-stage build then sets proj.mrr; 'pivot' sets a 2-day store boost. This switch is the publishing stage and the join between production and sales.
- PUBLISHING HAND-CARRY: finalize pushes {id, agentId, room, kind, payloadQ, flavor, due} to S.shipQueue (sim.js:253). WORLD walks the sprite to HERALD and calls SIM.heraldHandoff(shipId) (sim.js:326), which creates a 'publish' task for HERALD. minuteTick (sim.js:710) has a fallback: any ship past its 'due' is force-handed-off so a reload/party never loses a publish.
- SALES (FAKE REVENUE): salesTick (sim.js:359) runs every minute. For each Etsy store it computes a per-minute sale probability p = min(L,14)*0.00040 * (skill/60) * saleMult() * pivotBoost where L = S.listings[key], and on U.chance(p) books amt = U.rnd(rev[0],rev[1]) * revMult() via earn(). Assets/articles/songs have their own probability lines. Revenue is conjured from listing counts and dice — no buyers, no transactions.
- ECONOMY / COST MODEL (FAKE COST): two cost sources. (1) Per-task: taskCost(agentId) (sim.js:155) = U.rnd(model.costMin, model.costMax) * costMult(), where model is DATA.MODELS[agent.model] with hardcoded costMin/costMax per model (FABLE 1.40-3.10, OPUS 0.80-2.10, GPT 0.14-0.42 in data.js:7-11). Added to S.costs and ag.spent on every completeTask. (2) Daily subscription burn: dayRollover (sim.js:752) sums DATA.DAILY_SUBS[model] across all agents (FABLE 9.00, OPUS 7.50, GPT 4.20/day, data.js:12) * costMult() into S.costs. Net = S.rev.total - S.costs. These are the only two places 'token cost' exists, both pure RNG/constants.
- FEEDBACK-DRIVEN STAT GROWTH: feedback(fbId, verdict, note, opts) (sim.js:514). Commander verdicts (approve/deny/retry/archive) adjust the agent's morale/skill/autonomy and grant station xp. A non-empty note gives an extra skill/autonomy bump (sim.js:524). approve finalizes the held task with a +4 quality bump; deny/archive fail it; retry spawns a discounted retry task. agentNote() and praise/scold via chat also nudge skill/morale/autonomy. So 'training' is numeric stat deltas that feed back into rollQuality and the progress speed formula.
- ULTRON BRAIN (intent routing, faked NLU): playerMessage(raw) (sim.js:585) lowercases the text and regex-matches against INTENTS[] (sim.js:566) to pick an agent+kind and spawn a playerOrder task, plus party/status/help/praise/scold special cases. Replies are canned strings from DATA.C pools, delayed via queueUltron/queueChat into S.ultronQueue. No model is consulted.
- PERSISTENCE/AUTOSAVE: main.js save() (line 16) writes localStorage['starnet_save_v1'] = {sim: SIM.serialize(), settings}. SIM.serialize() (sim.js:826) = JSON.stringify({S, idc:U._id}); SIM.load() (sim.js:827) parses and re-inits from saved S. Autosave runs on setInterval(save, 30000) and on beforeunload (main.js:123-124). reset() removes the key and reloads. Whole game state is one JSON blob in localStorage.

**Real (reusable) logic.** Genuinely reusable, non-faked engineering: (1) The pipeline ARCHITECTURE — a producer/consumer inventory model (research increments S.insights, production consumes it, publishing increments S.listings, sales consume that) is a real, sound design that a real harness can keep. **How it works**

- MANIFEST-DRIVEN LOADING: assets.js init() fetches assets/sprites/manifest.json (no-store). manifest.sprites is {trackKey: [path,...]}. For each key it loads every PNG via new Image()/onload (loadImage, with null-on-error tolerance) and stores surviving Images in frames[key]. Readiness gate: only sets ready=true if frames['minion.rot.south'] exists.
- FRAME CONVENTION: one PNG = one frame (NOT a packed sprite sheet/atlas). File naming on disk is '<state>_<dir>[_<n>].png' (e.g. walk_south_0.png, rot_east.png, sit_north.png). The manifest re-keys these into dotted logical tracks '<set>.<state>.<dir>' (e.g. 'minion.walk.south'). Single-frame states (rot, sit) have no numeric suffix; multi-frame states (walk x4, drink x6, type x5) are zero-indexed arrays in draw order.
- DIRECTIONS: four cardinal — south/north/east/west. No diagonals. East/west are distinct PNGs (not mirrored in code). Minion frames are 40x40, Ultron 32x45 (verified by IHDR).
- ANIMATION STATE MACHINE (drawBody): chooses a track from body state via pick(set,names,dir) with graceful fallback (exact dir -> any dir of that name -> set.rot.south). Mapping: meeting->rot@4fps; walk->walk@10fps; working->type or sit facing north@6fps; social+sitting+hasCan->drink/sit south; sitting->sit/rot; idle->rot with a sine bob. Frame index = floor(now/(1000/fps)+phase) % frames.length, so each body's 'phase' desyncs identical agents.
- PALETTE-SHIFT RECOLOR (the 1-base-to-16-crew trick): the base minion suit is bright yellow, confirmed pixel value (255,255,40) ≈ HSL hue 50, matching constants BASE_HUE=50/BASE_SAT=0.85. filterFor(agentId) converts the agent's color hex to HSL and builds a CSS canvas filter: hue-rotate(agentHue-50 deg) + saturate(s/0.85, clamped 0.1–2) + brightness(0.85+l*0.45, clamped 0.75–1.25). tintFrames applies this filter while drawImage-downscaling each frame onto a per-(agent|track) cached canvas (imageSmoothingEnabled=false for crisp nearest-neighbor). So recoloring is a GPU canvas filter over the whole sprite, not a palette LUT — cheap, cached once per agent+track. Ultron is exempt (returns '' filter, keeps native red).
- SCALE: SCALE={minion:2/3, ultron:0.85}. Sprites authored at ~40px are downscaled to fit 12px tiles; Ultron downscaled less so he towers ~2x over crew. Downscale happens once at tint time and is cached.
- FURNITURE (separate, procedural): render.js iterates MAP.furniture and calls SPR.drawFurn(f). drawFurn looks up F[f.t] (a draw function) and calls it with pixel rect — it draws the prop with px() primitives. The 'work' flag (an agent working within 2 tiles) is passed so props can light up. There is NO image load for furniture; the PNGs and furniture/manifest.json are dead assets.
- FALLBACK: if SPRITES.ready is false (manifest/PNGs missing), drawAgent falls back to drawProcedural — a fully hand-coded pixel agent using body.color directly. So the sim renders even with zero PNG assets.

- PIXELLAB->MANIFEST BRIDGE: write an adapter that takes PixelLab output (4/8 directional frames + named animations like walk/drinking/picking-up + states like 'sitting down') and emits frame PNGs + a manifest.json in v7's exact '<set>.<state>.<dir>' scheme. PixelLab's directions (south/north/east/west + diagonals) and animation names map cleanly onto v7's rot/walk/sit/type/drink tracks.
- PER-AGENT ASSET NAMESPACING: today there are two hardcoded sets (minion, ultron). For N user agents you need per-agent sprite namespaces (e.g. assets/agents/<agentId>/manifest.json + frames) so the loader can scope frames[] by agent and avoid key collisions. Generalize assets.js's single global frames{} into per-agent (or shared-base + per-agent-tint) maps.
- 8-DIRECTION SUPPORT: assets.js only handles 4 cardinal dirs. PixelLab defaults to 8. Either request n_directions:4 from PixelLab to match, or extend pick()/dir handling to diagonals.
- FURNITURE AS PLACEABLE OBJECTS: the 'place a computer, agent walks to it and works' loop needs furniture to be runtime-placeable instances (not a static map.js array) with collision/sit/work-anchor metadata. Reuse the F procedural table or the PNG set, but rebuild placement as data-driven runtime state.
- DOWNSCALE/SIZE GENERALIZATION: SCALE is a hardcoded {minion,ultron} map. Make per-avatar scale a manifest field so generated avatars of varying source sizes render at consistent tile scale.

**Integration points (where real model/tool/cost plug in)**

- assets.js filterFor() reads DATA.AGENT[agentId].color — this is the single seam where a real user-chosen avatar color plugs in. Point it at the new agent store and recolor works immediately.
- assets.js init() fetch('assets/sprites/manifest.json') — the seam for swapping in per-agent or PixelLab-generated manifests; make the path/agent-scoped.
- sprites.js drawAgent() — already branches SPRITES.ready ? drawBody : drawProcedural. This is the clean seam: real PixelLab sprites when present, procedural fallback otherwise.
- map.js furniture[] + render.js drawFurn loop — the seam where 'placed objects' (computer, desk) become things an agent can walk to and sit/work at; the work flag + pw/pwl prop-window tags are where a placed 'computer' would bind to a real agent work session / cost readout.
- PixelLab MCP (create_character -> animate_character/create_character_state -> get_character download) is the runtime generation seam feeding the manifest bridge for the Terraria-style creator.
- drawBody returns overlay geometry {top,w,h} — the seam where real per-agent live cost/usage badges, selection box, and status overlays attach above the sprite.

**Risks**

- The furniture PNGs are a trap: a naive 'copy the furniture sprites' will copy 50 images that the original never used. The real furniture art is CODE (procedural F table). Decide deliberately: reuse procedural code, or commit to wiring the PNGs (new loader required).
- Recolor is a global hue-rotate over the WHOLE sprite, not a masked palette swap — it shifts skin/visor/can colors too, not just the suit. Fine for the stylized minion (mostly suit) but PixelLab avatars with rich multi-color palettes will recolor weirdly. For generated avatars, prefer generating the final color directly (PixelLab description/state) over hue-rotating.
- 4-direction-only assumption in assets.js vs PixelLab's 8-direction default — mismatch will drop diagonal frames unless reconciled.
- manifest readiness gate is hardcoded to frames['minion.rot.south']; for user agents this key won't exist — the gate must be generalized or the whole pipeline silently falls back to procedural.
- SCALE and frame sizes (40x40 minion, 32x45 ultron) are hardcoded; PixelLab sizes (configurable, e.g. 48px on ~68px canvas) differ and need per-avatar scale metadata or sprites render at the wrong tile size.
- PixelLab generation is async (~2-5 min/character, more for animations) and costs credits/generations — the 'wake up like a baby' onboarding must mask this latency (pre-generate, or animate the recolor-base minion first, then hot-swap the real avatar when ready).
- meta{fw,fh} is dead code; don't assume it carries frame dimensions when porting.
