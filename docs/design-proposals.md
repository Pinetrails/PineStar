# Design Proposals

_Three parallel design tracks: system architecture, gamified UX, monetization & safety (2026-06-13)._

## Technical architecture for the real agent-harness desktop app (gen folder) — desktop shell, process/runtime model, agent runtime, object→tool capability mapping, persistence, and v7 reuse plan.

**Recommendation.** Build a Tauri (Rust shell) desktop app with a sidecar Node.js "agent host" process. The v7 vanilla-JS canvas world (renderer, map, movement, sprites, sound, theming, boot) is reused almost wholesale as the Tauri webview frontend. The Node sidecar owns ALL secrets, model calls, tool execution, streaming, and cost metering; it talks to the frontend over a localhost WebSocket using the SAME U.bus event vocabulary v7 already uses internally (just real events instead of SIM-faked ones). Default provider is OpenRouter (one key, all of GPT 5.5 / Opus 4.8 / Fable 5 / any slug) with BYO-key support. The load-bearing abstraction: each placeable ROOM OBJECT is a capability grant — it registers (a) a sit/work anchor in the existing map, and (b) a set of tools the seated agent may call. An agent can only call a tool while physically seated at an object that grants it, and every tool runs sandboxed (computer→Docker/WSL2 shell+code; filing cabinet→a jailed per-agent workspace dir; phone/comms→allowlisted web/email). Real streaming token usage drives b.working and the in-game cost meters, so "sitting at the computer typing" literally means "a model/tool call is in flight" and the $ counter is real billed usage.

**Decisions**

- **Tauri (Rust core + system WebView2) for the desktop shell, NOT Electron** — Windows-first downloadable app: Tauri ships ~3-10MB installers vs Electron's ~85-150MB (no bundled Chromium — it uses the WebView2 runtime already on Win10/11). Built-in code-signed MSI/NSIS installers and a first-class auto-updater (tauri-plugin-updater with signed update manifests) cover 'downloadable + auto-update' out of the box. The v7 frontend is plain HTML/canvas/IIFE scripts with zero framework, so it drops into Tauri's webview unchanged — Tauri's webview-agnosticism is irrelevant here because we use almost no DOM APIs beyond canvas/localStorage. Lower memory footprint matters because the app also runs a Node agent host + possibly Docker. _(alt: Electron would let the agent runtime live in its Node main process (no separate sidecar, simpler IPC) and guarantees identical Chromium rendering everywhere — but the bundle size, RAM, and update payload are poor for a consumer desktop download, and WebView2 renders this simple canvas app fine. Pure web app rejected: needs local filesystem, local Docker/shell sandbox, and secret storage. Wails/Neutralino rejected: smaller ecosystems, weaker updater/signing story.)_
- **A Node.js sidecar 'agent host' process spawned by Tauri, not in-process Rust and not in the webview** — The agent ecosystem (Anthropic SDK, OpenAI SDK, OpenRouter, MCP clients, the existing OpenClaw gateway the user already runs on :18789) is JS/TS-native — reusing it in Rust would mean reimplementing SDKs. Tauri ships the sidecar as a bundled binary (pkg/Node SEA) and supervises its lifecycle. Keeping agents OUT of the webview is mandatory: secrets and tool execution must never live in renderer-reachable code (the v7 risk doc explicitly flags shipping API keys in client code). _(alt: In-process via Tauri Rust commands: forces a Rust agent loop, loses the JS SDK ecosystem and the user's existing OpenClaw/OpenRouter Node setup. Running agents in the webview: unacceptable secret exposure and no real sandbox.)_
- **Frontend↔sidecar transport = localhost WebSocket carrying the existing U.bus event schema; secrets only in the sidecar** — v7 is already a pure event-bus architecture (SIM emits 'deliverable'/'flagged'/'sale'/'chat'; WORLD and UI subscribe via U.bus). Replacing SIM with a WS client that re-emits real events ('agent.run.start', 'agent.tool_call', 'agent.token', 'agent.cost', 'agent.run.end', 'deliverable.ready') onto the same U.bus means WORLD/RENDER/PROPTERM need almost no change — they already react to these shapes. WebSocket (vs Tauri IPC) gives natural server→client streaming for token deltas and decouples the agent host so it could later run remotely. Keys live in OS keychain via tauri-plugin-stronghold / Windows Credential Manager, read only by the sidecar; the webview never sees them. _(alt: Tauri invoke/emit IPC: works but couples the runtime to Tauri and is clunkier for high-rate token streaming; chosen WS keeps the runtime portable and the seam identical to v7's bus. HTTP polling: wrong for streaming. Stdin/stdout pipe to sidecar: brittle for bidirectional structured streams.)_
- **OpenRouter as the default multi-model gateway, with direct-provider and BYO-key fallbacks; real metered cost from response usage** — The vision explicitly wants 'GPT 5.5, Opus 4.8, Fable 5, any via OpenRouter' at character creation — one OpenRouter key unlocks all model slugs and returns normalized usage (prompt/completion/cached tokens) plus per-call cost in the response, which feeds the cost meter directly and honestly. This replaces taskCost()/estCost()'s fake U.rnd ranges. The user already runs OpenRouter locally. Direct Anthropic/OpenAI clients are kept as adapters for users who want them or for prompt-caching/streaming features OpenRouter underexposes. _(alt: Direct-only (Anthropic+OpenAI): loses arbitrary OpenRouter slugs and forces per-vendor key management at creation. Routing through the user's existing OpenClaw gateway is supported as an adapter but not the default, since a downloadable app can't assume :18789 is running.)_
- **Run-state→animation mapping driven by real streaming lifecycle, reusing v7's b.working/plan sequencer unchanged** — v7 already has the exact loop: goTo(seatTile)→arrive() sits the agent, and b.working drives the type/sit sprite track. We re-point b.working from SIM.taskId to 'a real model/tool call is open'. Mapping: agent.run.start → plan a walk to the object's seat → on arrival, dispatch the real call and set sitting=true; agent.token deltas → keep working=true (and stream into the prop-terminal); agent.tool_call → set act string to the real tool name; agent.run.end → stand/clear. think() must treat an open real call like hasTask so the body doesn't wander mid-call. _(alt: Inventing a new movement system: wasteful — v7's plan sequencer ({go/face/sit/wait/do}) is already a clean coroutine for physical errands. Cosmetic-only animation decoupled from real state: violates the 'truthful telemetry' design contract.)_
- **Object→Tool capability model: a placed object is a typed capability grant gated by physical seating + sandbox** — This is the product's core metaphor and its security model in one. An object instance = {type, tile, footprint, seat, facing, grants:[toolIds], sandbox}. computer→{shell.exec, code.run} in a Docker/WSL2 container scoped to that agent's workspace; filing cabinet→{fs.read, fs.write} jailed to ./workspaces/<agentId>/; phone/comms→{web.fetch, email.send} against a user-approved allowlist; easel/render→{image.generate} via PixelLab/image API. The agent runtime exposes to a model ONLY the union of tools granted by objects the agent is currently seated at. This makes capabilities literally visible/placeable (gamified) AND enforces least-privilege: no computer placed = no shell access, period. Every grant maps to a real MCP server or tool adapter in the sidecar. _(alt: Giving every agent every tool: unsafe and breaks the placement metaphor. A flat settings checklist for permissions: less legible and not diegetic. Per-object sandbox via OS user accounts: heavier than container/dir jails for a consumer app.)_
- **Persistence: SQLite (via the sidecar) for durable state; localStorage only for view/settings** — Real harness state outgrows v7's single localStorage JSON blob: agent configs (model, system prompt/purpose, avatar manifest ref, granted objects), world/object placements, full transcripts, tool-call logs, a usage/credits ledger, and in-flight job records all need queryable, durable, concurrent-safe storage that survives reload of in-progress runs. SQLite in the sidecar's app-data dir is the right desktop default; the v7 save/load/serialize pattern and its lazy-migration guards become the schema-migration discipline. Generated avatar PNGs/manifests and deliverable artifacts live on disk under the app-data dir, referenced by path. _(alt: Keep localStorage: caps out fast, no concurrency, loses in-flight jobs on reload, can't hold transcripts/artifacts. A heavier DB (Postgres) is overkill for a single-user desktop app.)_
- **Decouple game-time from real-call cadence; treat runs as async jobs with concurrency/credit backpressure** — v7's loop fires up to 30 game-minutes/frame and completes 'work' instantly and infallibly. Real calls are slow, failable, and cost money on error; at speed>1 the old loop would fan out many paid calls/sec. The runtime must model each run as a tracked async job (mirroring v7's reload-safe shipQueue/heraldHandoff pattern), with a concurrency cap, rate-limit handling, retry/timeout, and a credit-balance gate that replaces v7's cosmetic 5-job cap with real backpressure. _(alt: Keep the synchronous instant-completion loop: would burn credits uncontrollably and has no failure handling. Tie call cadence to game ticks: same problem.)_

**Components**

- **Tauri shell (Rust core)** — Window/WebView2 host, code-signed MSI/NSIS packaging, auto-updater, OS keychain access for secrets, spawning/supervising the Node agent-host sidecar, and brokering the few privileged ops (open file dialogs, app-data paths). _(reuses: none directly — new)_
- **Frontend world (webview)** — The pixel-art room: canvas render loop, tile map + BFS pathing, movement/sit/work state machine, sprite recolor/animation, sound, theming, boot/onboarding overlays, prop-terminal windows, click→inspect. Subscribes to real events over WS and renders them. _(reuses: render.js, map.js, agents.js (WORLD), assets.js (SPRITES), sprites.js (procedural fallback + furniture art), util.js (U/bus/SFX), css/style.css, index.html grid + #boot — reused wholesale)_
- **WS bridge / event adapter** — Replaces the SIM module: a thin frontend client that connects to the sidecar, translates real agent-host events into U.bus emits using v7's existing event names, and forwards user directives/feedback/placements back to the host. The single integration seam. _(reuses: the U.bus contract and SIM's public method surface (init/tick/serialize shapes) as the adapter interface)_
- **Agent host (Node sidecar)** — Owns secrets; runs the agent loop (model→tool calls→results→stream); per-agent session manager (live connection, tool registry, usage tally, deliverable buffer); concurrency/credit/rate-limit backpressure; emits the real event stream over WS. _(reuses: conceptual reuse of the task lifecycle (todo/active/review/done), shipQueue async-job tracking, and feedback/approval gate from sim.js — reimplemented against real calls)_
- **Provider adapters** — Uniform chat/stream/usage interface over OpenRouter (default), direct Anthropic, direct OpenAI, and the user's OpenClaw gateway; normalize streaming token deltas and real usage/cost out of each provider. _(reuses: DATA.MODELS record shape (extended with real per-1k pricing + slug) — schema reused, fake cost ranges dropped)_
- **Capability/tool registry & sandbox** — Maps object types→tool sets; enforces 'tool callable only while seated at a granting object'; executes tools sandboxed: computer→Docker/WSL2 container, filing cabinet→jailed workspace dir, phone/comms→allowlisted web/email, easel→image gen (PixelLab/MCP). Each tool is an MCP server or local adapter. _(reuses: map.js furniture schema {t,x,y,w,h,sit,pw} extended with grants[]/seat/sandbox — schema reused, placement made runtime-mutable)_
- **Cost & credits ledger** — Accumulates real billed usage per agent/run from provider usage fields, prices it, decrements subscription credits (Hermes-style $50/mo model) or BYO-key spend, and feeds the live per-agent cost meter and the click-to-inspect dossier. _(reuses: earn()/S.costs/ag.spent accounting structure and the prop-terminal meter UI (#ft/#fm/#fx) — UI reused, data source made real)_
- **Persistence layer** — SQLite store for agents, object placements, transcripts, tool logs, ledger, and in-flight jobs; disk store for avatar manifests and deliverable artifacts; schema migrations. _(reuses: save/load/reset orchestration + lazy-migration guard discipline from main.js/sim.js — pattern reused, backend swapped)_
- **Onboarding & avatar pipeline** — First-run flow: model pick → avatar design (live hue/sat/bright recolor of base minion, or PixelLab MCP generation → per-agent manifest) → name → 'waking up' animation → purpose chat (real model call) that writes the agent's system prompt. Placement/build mode for dropping objects. _(reuses: #boot overlay + bootSeq typewriter, assets.js filterFor/tintFrames recolor engine, chat-input UI, @keyframes power-on — reused; PixelLab bridge is new)_

**Data model**

- AgentConfig { id, name, model(slug+provider), systemPrompt/purpose, avatarManifestRef|recolorFilter, color, grantedObjectIds[], createdAt }
- ObjectInstance { id, type, tile{x,y}, footprint{w,h}, seat{tile,facing}, grants:[toolId], sandboxRef, spriteKey }
- ToolGrant / CapabilityRegistry { toolId, objectType, adapter(MCP|local), sandboxPolicy(container|jailedDir|allowlist), schema }
- RunJob { id, agentId, status(queued|walking|active|tool_calling|review|done|failed), objectId(seat), startedAt, finishedAt }  — durable, reload-safe (mirrors v7 shipQueue)
- TokenUsage / CostLedgerEntry { runId, agentId, model, promptTokens, completionTokens, cachedTokens, toolTokens, costUSD, ts }
- CreditsAccount { balanceUSD, plan, refillHistory[], byoKeyMode(bool) }
- Transcript { runId, messages[], toolCalls[{name,args,result,ts,costSlice}], deliverableRefs[] }
- Deliverable { id, runId, kind, artifactPath|url, createdAt }
- WorldState { roomDescriptor, objectInstances[], camera{x,y,zoom} } — replaces v7's hard-coded zones/furniture literals
- RuntimeEvent (WS/U.bus) { type: agent.run.start|agent.token|agent.tool_call|agent.cost|agent.run.end|deliverable.ready|directive|feedback|object.place, agentId, payload }

**Risks**

- Cost honesty is load-bearing: streaming token deltas often don't equal the final billed usage (cache reads, thinking tokens, tool-call tokens, provider rounding). The live meter must show a streaming estimate but reconcile to the provider's final usage/cost on run-end, or the 'see what it's costing you' promise erodes trust.
- Sandbox escape / destructive tools: a 'computer' granting shell/code execution is the highest-risk capability. Must default to a container (Docker Desktop/WSL2) jailed to the agent's workspace with no host mount, network allowlist, and resource caps. Docker may be absent on a consumer Windows box — need a graceful 'shell unavailable until you install/enable WSL2' fallback so placing a computer doesn't silently fail or run unsandboxed.
- Secret handling in a downloadable app: the OpenRouter/provider key must live in OS keychain read only by the sidecar, never in webview-reachable code or the SQLite blob. The subscription-credits proxy model (server-side key) vs BYO-key (local key) must be designed so client code never embeds a shipped key.
- Runaway spend: real async paid calls + game-time fan-out can burn credits fast. Needs a hard concurrency cap, per-run/per-day budget guards, credit-balance gating before dispatch, and retry-loop limits (esp. the feedback 'retry' path) — none of which v7's free simulation needed.
- Streaming cadence mismatch: model output arrives in bursty chunks and tool calls are atomic, but the prop-terminal expects ~7fps smooth char-by-char. Need a typewriter buffer that drains real tokens at a steady visual rate, decoupled from network arrival, or the feed looks janky.
- Transcript growth vs the 1/sec full-rerender: v7 rebuilds window bodies via innerHTML with lines capped at 9. Real long transcripts will thrash and lose scroll/selection — streaming must append to a stable scrollback element, not rebuild it.
- Dynamic single-agent roster breaks fixed-17 assumptions: WORLD/SIM/UI/propterm iterate DATA.AGENTS and assume per-id stations, rooms, buddies, and DEFS keys. First-launch single user agent will hit many null paths (beltInfo, heraldSpot, buddy, station) — needs defensive guards and runtime station/room allocation.
- Runtime object placement fights v7's bake-once world: placing a computer requires updating zoneGrid/blocked/sitTiles/pwGrid AND re-baking baseCv/lightCv (no invalidate API today), plus a camera for rooms larger than the fixed 936x674 buffer (touches both render transform and toLocal hit-testing).
- PixelLab avatar generation is async (~minutes) and credit-billed; the 'wake up like a baby' onboarding must mask latency (animate the recolored base minion first, hot-swap the real avatar when ready) and the global hue-rotate recolor will distort multi-color PixelLab palettes — prefer generating the final-colored avatar over hue-rotating it.
- Sidecar lifecycle/ports: the Node host must be supervised (restart on crash without losing in-flight job records — hence durable jobs in SQLite), bind to a random localhost port handshaked to the webview, and shut down cleanly with the app to avoid orphaned processes holding secrets.

**Open questions**

- Business model fork: ship a server-side credit proxy (Hermes-style $50/mo, your OpenRouter key, you bear billing + abuse risk + need a backend service) OR BYO-API-key only (no backend, user pays provider directly, simpler/safer to ship) OR both with BYO as the launch default and credits added later? This decision drives whether you need any cloud infrastructure at all for v1.
- Sandbox dependency fork: require Docker Desktop/WSL2 for the 'computer' shell/code capability (powerful but a heavy install prerequisite that will lose non-technical users) OR ship a lighter built-in sandbox (jailed Node VM / restricted subprocess, weaker isolation) OR gate shell behind an explicit 'advanced mode' and ship only safe tools (file/web/image) by default?
- Single-room vs multi-room scope for v1: keep v7's fixed station layout and just make objects placeable within it (fast, reuses all baked geometry), OR build the full data-driven mutable world + camera now (matches the long-term vision but is the largest rebuild and the biggest source of risk)?
- Multi-agent at launch or single-agent first: the vision starts with creating ONE agent; do agents actually collaborate/hand off work to each other (requiring inter-agent messaging, the HERALD-style ceremonies made real) in v1, or is v1 strictly one-user-agent-at-a-time with multi-agent deferred?
- Deliverable destinations: are real outputs (images, code, articles) just saved to disk and shown in-game, OR do you wire real publishing/marketplace tools (Printify, Fiverr, Medium, YouTube) so the agent can actually ship — and if so, which integrations are in-scope vs aspirational set-dressing for v1?
- Quality/review signal: drop v7's fake rollQuality entirely and rely solely on human (Commander) approval in the feedback gate, OR add a real LLM-judge/automated-eval that itself costs tokens and must be budgeted?
- Do you keep any notion of simulated 'revenue/economy' for game feel, or fully replace the economy with credits-spent + deliverables-shipped (the honest agent-harness framing the analysis recommends)? This changes the entire right-panel/treasury UI and the core feedback loop.

## Gamified Player Experience — onboarding, core placement loop, multi-agent growth, real cost surfacing, and the GOALS.md aesthetic mapped onto a real agent harness

**Recommendation.** Frame the whole product as "raise and run a real AI crew on a space station." Reuse v7's shell/theme/boot/recolor/movement engines verbatim and replace only the data sources. Onboarding is a 6-screen diegetic ritual (CRADLE BAY) that produces a real agent config (model id + system prompt + tools + avatar) — never a settings form, always in-fiction. The core loop is Terraria-style: a freshly-woken agent wanders an empty quarters; the user opens BUILD MODE and drops a COMPUTER prop; the agent paths to it, sits, and `b.working` is now driven by a REAL streaming model session, not SIM.taskId. Clicking the seated agent opens the prop-terminal as a live transcript with truthful token/cost/context meters sourced from real API usage. Growth is literal real-estate: earn/buy room modules, recruit more agents through the same CRADLE ritual, and the 17-agent "Skynet" station becomes the aspirational end-state of a crew the user grew one wake-up at a time. Honor GOALS.md by making every principle LITERALLY true now that the data is real: movement = a real call in flight, telemetry = real usage, the terminal = a real session.

**Decisions**

- **Onboarding is a diegetic 6-screen ritual ('CRADLE BAY'), not a setup wizard — model pick, avatar design, naming, wake-up animation, and purpose chat all happen in-world over the existing #boot CRT overlay layer.** — GOALS principle 5 (diegetic terminal, no OS chrome) and principle 10 (fiction mirrors the real stack). The user is 'taking command', not 'configuring software'. Reuses main.js bootSeq typewriter + #boot z-2000 overlay + CRT styling wholesale; the boot click-gate already solves the WebAudio autoplay unlock that the wake-up sound needs. _(alt: A conventional multi-step form modal — rejected: violates the no-chrome design contract and kills the emotional 'birth' beat that makes the agent feel owned.)_
- **The 'give it purpose' chat is a REAL model call whose TRANSCRIPT is compiled into the agent's persisted system prompt — the onboarding conversation IS the prompt-authoring tool, surfaced as raising a newborn.** — Directly satisfies the vision ('gamified onboarding configures the real agent's system prompt/role'). Reuse the #chat-input + bubble UI (ui.js:441) but repoint SIM.playerMessage at the OpenClaw gateway (localhost:18789) / OpenRouter. A lightweight 'midwife' orchestrator interviews the user, then emits a structured AgentConfig {role, goals[], tools[], constraints[], tone} that is templated into the real system prompt. The raw chat is kept as 'first memories'. _(alt: A plain textarea 'paste your system prompt' — rejected: not gamified, and most users can't author a good prompt cold. The interview extracts it.)_
- **Avatar designer offers two tracks on ONE screen: (A) INSTANT — live hue/sat/bright sliders over the recolored base minion (filterFor/tintFrames already does this, zero latency), and (B) FORGE — a PixelLab text-prompt generation that hot-swaps the real sprite in when ready. A starts selected so the agent can wake immediately.** — assets.js filterFor() is a working real-time recolor engine — exposing its three filter params as sliders is near-free and gives instant Terraria-style customization. PixelLab generation is async (2-5 min) and credit-billed, so it must NOT block the wake-up; track A is the masking layer (per the risk flagged in the asset-pipeline analysis: 'animate the recolor-base minion first, then hot-swap'). _(alt: PixelLab-only — rejected: latency/cost would stall first-launch and require a network round-trip before the user sees their character. Slider-only — rejected: under-delivers on the 'DESIGN a pixel-art avatar' promise.)_
- **The core loop is gated on PHYSICAL PLACEMENT: a real task can only run once a COMPUTER prop exists and the agent has walked to it and sat. No computer placed => the agent literally cannot work, only wander.** — Makes 'movement is meaning' (GOALS 1) LITERAL — the sit-at-computer animation becomes the true and only visual of a real session. Reuse WORLD.goTo(seatTile)+arrive() and the {go/face/sit/do} plan sequencer (agents.js:190); generalize stations{} so a placed computer registers a sit tile + work anchor (the rebuild item already identified). Teaches the mechanic by withholding it: the empty room creates the desire to place the object. _(alt: Auto-spawn a desk on wake — rejected: removes the player-agency placement beat that is the heart of the requested Terraria loop.)_
- **b.working / f.work is rebound from SIM.taskId to a real SessionManager flag: true only while a model request or tool call is in flight, cleared on completion. The lit screen, typing arms, and CRT bloom stay cosmetic but their TRIGGER is real.** — This is THE seam the rendering analysis names (agents.js:471 think(), consumed by drawBody assets.js:90 and every F.* furniture fn). Satisfies GOALS 2 (truthful telemetry — the screen lights mean a real call). Keeps the entire render/animation layer untouched. _(alt: Keep a fake progress timer alongside real calls — rejected: reintroduces the 'decorative lie' GOALS 2 forbids and desyncs the animation from real latency.)_
- **Clicking a seated agent opens the prop-terminal (PROPTERM.open) as a REAL streaming session: a typewriter buffer drains real token deltas at a steady rate, '▶ tool / ◀ result' lines are real tool_use/tool_result events, and the token/cost/context meters read real usage from the provider.** — Reuses propterm.js streamHTML/feedHTML/fastTick id-targeted DOM patching and the FEED state machine; replaces only nextLine() (the named #1 seam) with a real per-agent event queue, and estCost/ctxPct with real usage. The typewriter buffer decouples smooth ~7fps visuals from bursty network arrival (the cadence risk flagged in the propterm analysis). _(alt: A separate plain chat log window — rejected: throws away the diegetic CRT terminal that is the product's signature surface.)_
- **Real per-agent cost surfaces in THREE diegetic tiers (interaction grain ratchets down, GOALS 6): (1) ambient — a small $/hr burn chip floats above a working agent's head and the topbar shows live total spend + credits remaining; (2) click — the agent dossier shows session count, tokens, real $ spent today/total, and a live cost-rate sparkline; (3) deep — the prop-terminal's TOK/COST/CTX meters tick against the actual in-flight call.** — Delivers 'see how much it's costing you' as a progressive-disclosure instrument panel, matching GOALS 6 (room→agent→prop). Reuses the topbar revenue/NET slot (repurposed to SPEND/CREDITS), openAgent dossier (ui.js:226), and the propterm meters. Every number traces to a real usage value (GOALS 2 becomes a hard requirement). _(alt: A single global billing page — rejected: not diegetic, and breaks the per-agent 'how much is THIS one costing me' framing.)_
- **Growth is real-estate + recruitment: the user starts with ONE agent in ONE quarters; completing work / spending credits earns STATION XP that unlocks buyable room modules (each a placeable zone) and additional CRADLE slots. Each new agent goes through the same wake-up ritual.** — Turns the static 17-agent fiction into an earned, user-grown crew (the vision's 'user-grown crew'). Reuses the XP/level/perk/milestone progression (real engine plumbing per the sim analysis) but re-points its rewards from fake economy unlocks to real capacity (room slots, agent slots, tool unlocks). The existing Skynet station becomes the visible 'end-game silhouette'. _(alt: All rooms/agents available immediately — rejected: removes progression and the sense of building an org; also uncaps real spend with no pacing.)_
- **Game-time is fully decoupled from real call cadence: the rAF loop drives only animation/wander; real model calls fire ONLY on real triggers (user directive, scheduled job, agent-initiated step), never per game-minute. Speed-up affects ambient motion, never call frequency.** — Directly mitigates the top risk in the sim analysis ('at speed>1 the loop fans out many paid calls/sec — burns money uncontrollably'). The fake minuteTick generator that spawned tasks on a timer is deleted, not rebound. _(alt: Keep the heartbeat spawning tasks at reduced rate — rejected: any time-driven auto-dispatch of paid calls is a financial footgun for a downloadable app with the user's key/credits.)_
- **Drop simulated revenue entirely; the 'economy' becomes credits-spent + deliverables-shipped. Topbar NET/REV slots are repurposed to CREDITS REMAINING + WORK SHIPPED; the $50/mo subscription grants credits, with BYO-API-key as an alternate fuel source.** — The sim analysis is decisive that fake sales 'structurally cannot be made real without marketplace/payment integrations' and the honest path is to meter real cost + real output. Aligns the in-game economy with the actual business model (Hermes-style credits). _(alt: Keep simulated Etsy/Fiverr sales for game feel — rejected: violates GOALS 2 truthful-telemetry and sets a dishonest expectation in a real-money product.)_

**Components**

- **CradleBay (onboarding controller)** — Full-screen 6-screen diegetic ritual: S1 INTAKE (model pick) -> S2 FORGE (avatar designer: sliders + PixelLab) -> S3 DESIGNATION (name) -> S4 IGNITION (wake-up 'baby' animation) -> S5 PURPOSE (real interview chat) -> S6 COMMISSION (review + drop agent onto floor). Owns onboarding state and writes the final AgentConfig. _(reuses: main.js #boot overlay + bootSeq typewriter + CRT styling; SFX.boot/level for beats; ui.js #chat-input + bubble UI for S5; assets.js filterFor/tintFrames live preview for S2.)_
- **ModelPicker (S1)** — Lists real OpenRouter/gateway models (GPT 5.5, Opus 4.8, Fable 5, arbitrary slugs) as diegetic 'core uplink' cards showing real per-token pricing and a one-line temperament blurb. Captures {modelId, vendor, pricePerMTokIn/Out}. _(reuses: DATA.MODELS record shape (extended with real ids + live pricing instead of invented costMin/costMax); the .term card styling.)_
- **AvatarForge (S2)** — Live canvas preview of drawBody with two tracks: INSTANT (hue/sat/bright + scale sliders over base minion, applied via the existing CSS filter) and FORGE (PixelLab text prompt -> create_character/animate_character -> hot-swap frames into SPRITES.frames under a per-agent key). Captures {filter | spriteKey, scale}. _(reuses: assets.js filterFor/tintFrames/drawBody verbatim as the recolor backend; SCALE generalized to a per-avatar manifest field; PixelLab MCP (create_character/animate_character) for track B.)_
- **PurposeInterview (S5) + ConfigCompiler** — Runs a real 'midwife' orchestrator chat that asks the user what the agent is for, in gamified newborn framing. **Risks**

- Wake-up latency trap: PixelLab generation (2-5 min, credit-billed) cannot block S4 IGNITION. The avatar MUST wake as the slider-recolored base minion and hot-swap when frames arrive; if the hot-swap path or readiness gate (hardcoded to 'minion.rot.south') isn't generalized per-agent, the whole pipeline silently falls back to procedural and the user's PixelLab avatar never appears.

The TOK/COST meters must reconcile streamed estimate with the final usage report or the 'see how much it's costing you' promise erodes trust — the exact thing the product sells.
- Streaming cadence mismatch: model output arrives in bursty chunks and tool calls are atomic, but the UI assumes smooth ~7fps char-by-char typing. Without a typewriter drain buffer the live terminal looks janky; with too-deep a buffer the agent 'finishes typing' while the real call is still running, desyncing the sit animation from real latency.
- Placement/bake coupling: every placed/moved object must update zoneGrid, blocked, sitTiles, AND pwGrid plus re-bake baseCv/lightCv. Miss one and agents walk through objects, no sit tile registers, or the click-to-open-terminal target is wrong. There is no invalidate/rebuild API in v7 today — it must be built deliberately.
- No camera exists (fixed 936x674 buffer). A user-grown multi-room station will exceed the viewport; adding pan/zoom touches both rendering (transform before world layers) and input (toLocal must invert it) — easy to half-implement and break hit-testing.
- Single-agent first-launch hits many roster null-paths: stations, buddies, HERALD/ULTRON ceremonies, belts all assume the fixed 17-agent station. The journey planners (onDeliverable/planBriefing/planVisit) need null-guards and dynamic station allocation or they crash/no-op for a lone newborn agent.
- Onboarding-chat-to-system-prompt fidelity: if the ConfigCompiler mis-extracts the user's intent, the agent's real behavior won't match what the user thought they raised. The compiled prompt should be reviewable/editable at S6 COMMISSION so the gamified extraction is auditable, not a black box.
- Secrets handling: a downloadable desktop app must never embed the OpenRouter/OpenClaw key in client code. BYO-key and a subscription-credit proxy must be designed so the key stays in ~/.openclaw / OS keychain, never in the shipped bundle.
- abortPlan/flush double-fire: v7's flush() guarantees a side-effect fires even if a walk is interrupted (fine for fake handoffs). With real work, a cancelled walk-to-computer must NOT still mark a deliverable shipped or kick a real (paid) call — flush semantics need rethinking for real actions.
- Google Fonts VT323 CDN dependency breaks the offline promise for a downloadable app (already flagged in GOALS Loop D) — vendor the font locally.

**Open questions**

- Fuel model at launch: subscription-credits-only ($50/mo Hermes-style), BYO-API-key-only, or both? This changes onboarding (S1 must ask for a key if BYO), the cost HUD framing (credits vs raw $), and the secrets/proxy architecture. Recommendation leans 'both, subscription default' but it's a real business fork.
- When does an agent's real work actually trigger? Three models: (a) PURE PULL — agent only acts on an explicit Commander directive; (b) SCHEDULED — user sets recurring jobs (the scheduled-task MCP) that fire real calls; (c) AUTONOMOUS — agent self-initiates steps toward its purpose. (c) is the most 'alive' but the scariest for runaway spend. Which is the default, and is autonomy a per-agent toggle the user grants during onboarding?
- Do we keep ANY simulated economy for game-feel, or go fully truthful (credits-spent + work-shipped only)? Dropping fake revenue is the honest/recommended path, but it removes the satisfying 'money goes up' dopamine loop — is 'deliverables shipped' + 'station grows' a strong enough reward substitute?
- Multi-agent coordination: when the crew grows, do agents actually collaborate (real inter-agent message passing / a real orchestrator 'ULTRON' delegating), or is each agent an independent worker and the org structure is purely cosmetic? Real multi-agent orchestration is a large scope jump vs. reusing the HERALD/ULTRON walk choreography as flavor over independent agents.
- Avatar generation default: is the PixelLab FORGE track a premium/credit-gated feature (it costs real generations) with slider-recolor as the free default, or is bespoke generation core to first-launch for everyone? Affects onboarding pacing and credit economics.
- Tool grants during onboarding: should the PURPOSE interview let the user grant real tool/MCP permissions (file write, web, image gen, publish) per agent, and how is that surfaced gamified (e.g. 'equipping' the agent with tools as items)? This is where real capability — and real risk — enters.
- Persistence + concurrency target: localStorage is outgrown by real transcripts/usage ledgers/artifacts. Desktop shell — Electron vs Tauri vs staying vanilla-served — determines fetch/CORS, file access, keychain, and whether the global-IIFE no-build architecture survives or needs modules. This is foundational and should be decided before the harness is built.

## Monetization, Billing & Trust/Safety layer for the "gen" desktop harness (real-agent conversion of v7/Skynet)

**Recommendation.** Launch with HYBRID billing that defaults to "Bring Your Own Key" (BYOK) — store the user's OpenRouter/Anthropic key locally and pass real metered usage through unchanged — and ship the managed-credits "Station Pass" ($50/mo grants $50 of usage at cost, app keeps a separate ~25-30% platform margin baked into a higher displayed rate) as an opt-in path behind a thin hosted proxy. BYOK gets you to market in weeks with ZERO upstream-key liability, no proxy infra, no payment/PCI exposure, and no money-transmitter/credit-balance regulatory questions; it also makes the "see how much it's costing you" promise trivially honest because you read real usage off the provider response. The credits model is the real business but it requires a hosted billing proxy + Stripe + a ledger service you do not need on day one. Crucially: BYOK and managed-credits share ONE internal cost engine and ONE in-game spend UI (repurpose v7's LEDGER/treasury_ledger window, ag.spent, estCost meters, TOP BURNERS, DAILY LEDGER) — only the *source of the dollar number* and *who holds the upstream key* differ, so shipping BYOK first costs nothing toward the credits build. Gate all real tool execution (shell/files/web) behind the EXISTING object-placement mechanic as the capability surface: an agent can only do what the room contains — placing a "computer" grants compute, a "terminal/console" prop grants shell, a "filing cabinet" grants disk, an "uplink/web" prop grants network — turning v7's set-dressing into a literal, legible permission system.

**Decisions**

- **Ship BYOK-first, credits-second (hybrid), not credits-first or pure-BYOK-forever** — Pure BYOK can ship in weeks with no proxy, no Stripe, no upstream-key custody, no balance/escrow regulatory exposure, and makes truthful telemetry (GOALS principle 2) trivial since usage comes straight off the provider response. But BYOK alone leaves the $50/mo Hermes-style revenue on the table and asks non-technical users to obtain an API key. Hybrid keeps the fast launch AND keeps the managed-credits business as a flip-the-switch upgrade because both paths feed ONE cost engine and ONE spend UI. _(alt: Credits-first (blocked on proxy+Stripe+ledger+key custody+possible money-transmitter analysis before any launch); pure BYOK forever (no recurring revenue, high signup friction, no margin).)_
- **For managed credits, route ALL model traffic through a thin hosted proxy (gen-gateway) that holds the upstream keys; the desktop app NEVER ships an upstream key** — CLAUDE.md already flags shipping the OpenRouter key in client code as a secrets risk. A desktop binary is fully inspectable, so any embedded key is immediately extractable and abusable. The proxy holds platform keys server-side, authenticates the app with a per-account short-lived token, meters tokens, applies markup, decrements the credit ledger, and streams the response back. This is the same pattern the local OpenClaw gateway (:18789) already proves out — repoint the runtime from localhost:18789 to the hosted gateway for credits-mode, keep :18789 for local/BYOK power users. _(alt: Embed a platform key in the app (immediately extractable, unbounded liability); per-user provisioned upstream keys (provider ToS issues, no central metering/markup, hard to revoke).)_
- **Display real $ at a marked-up rate in credits-mode, real $ at provider-cost in BYOK-mode, from one cost engine** — The credit price = upstream cost x (1 + margin). To keep the in-game meter honest AND profitable, the gateway returns the *billed credit amount* (already marked up) as the authoritative number; the app shows that. In BYOK mode the same engine shows raw provider cost (markup=0). One CostEngine.price(usage, rateCard) function with a per-mode rate card means the LEDGER UI, ag.spent, and estCost are identical code in both modes. _(alt: Two separate cost paths (drift, double-maintenance, risk of showing a number that doesn't match the bill — directly violates the truthful-telemetry design contract).)_
- **Decouple in-game time from real call cadence; meter on real usage events, not the sim minute-tick** — v7's loop fires up to 30 game-minutes/frame and at speed>1 would fan out many paid calls/second, burning credits uncontrollably (flagged in the sim subsystem risks). Real billing must be driven by actual streaming usage events (token deltas + final usage report), reconciled to the final provider usage number, NOT by t.prog/t.dur. The sit-at-computer animation starts on real call-begin and ends on real call-return. _(alt: Keep sim-clock-driven cost (mints fake numbers, decouples spend from reality, runs up real bills at high sim speed).)_
- **Reconcile streaming token estimates against the FINAL provider usage report before committing to the ledger** — Streaming token deltas often do not equal the final billed usage (cache reads, thinking tokens, tool-call tokens) — flagged in the propterm subsystem risk. Show a live *estimate* during streaming (estCost-style), then on call completion overwrite ag.spent with the authoritative usage*rate from the provider/proxy response so the committed ledger never drifts from the real bill. _(alt: Trust streaming deltas only (meter subtly wrong, erodes trust); only show cost at the end (loses the live 'watch it cost you' drama that is the product hook).)_
- **Make object placement the capability/permission surface; no ambient tool access** — Real agents executing shell/files/web on the user's machine is the single biggest risk. v7 already has the perfect legible metaphor: an agent can only act through props in its room. Reify it — a placed 'computer' = model compute; 'terminal/console' prop = shell tool (scoped to a sandbox dir); 'filing cabinet' = filesystem read/write (scoped); 'uplink/satellite' prop = network/web. Removing the object revokes the capability. This is both UX and security: the room IS the allow-list, and it's visible. _(alt: Global tool permissions in a settings menu (invisible, easy to over-grant, no in-world meaning); always-on tools (unacceptable risk on a user's machine).)_
- **Default-deny tool execution with per-action permission prompts + a sandboxed working directory; agents cannot touch arbitrary paths** — Even with object-gating, the FIRST time an agent in a session wants to run a shell command, write a file, or hit a domain, prompt the user (allow once / allow for session / always allow this agent+capability / deny), and confine file/shell ops to a per-agent workspace directory by default. Note CLAUDE.md says bypassPermissions is set for THIS dev instance — that must NOT carry into the shipped product; shipped default is prompt-on-first-use. _(alt: Trust the agent (catastrophic on a real machine); allowlist-only with no prompts (too rigid, users hit walls); inherit the dev bypassPermissions default (ships a footgun).)_
- **Repurpose v7's LEDGER agent + treasury_ledger (TRS-01) window + ag.spent/estCost/TOP BURNERS/DAILY LEDGER as the real billing dashboard** — These surfaces already exist and already render per-agent BURNED (ag.spent), an estCost meter, a sorted TOP BURNERS list, and a DAILY LEDGER history (confirmed in data.js:80 LEDGER agent, propterm.js:799 BURNED, :1236 treasury_ledger, :1273 TOP BURNERS). Swap their data source from taskCost()/DATA.DAILY_SUBS RNG to the real CostEngine and they become the production billing UI with near-zero new UI code. Add a CREDITS REMAINING gauge and a low-balance warning to the topbar (which already shows revenue/NET). _(alt: Build a new billing UI from scratch (wasteful — the diegetic CRT ledger is a product differentiator and already built).)_
- **Distribute as a code-signed Windows installer (NSIS/MSI via Electron-builder or Tauri) with auto-update; accounts only required for credits-mode** — Desktop-app target implies Electron or Tauri (flagged in app-shell risks). Tauri gives a smaller, more secure binary (Rust core, system webview) which suits a security-sensitive agent harness; Electron is faster to port the vanilla-JS shell verbatim. Either way: an EV/OV code-signing cert avoids SmartScreen scares, and a signed auto-update channel (Squirrel/Tauri updater) is mandatory for shipping security fixes to a tool that runs real code. BYOK-mode needs no account (key is local); credits-mode requires a lightweight account tied to Stripe. _(alt: Unsigned zip (SmartScreen blocks, no trust, no auto-update — unacceptable for a tool that runs shell on user machines); web app (can't do local shell/files, defeats the vision).)_
- **Vendor fonts/assets locally and treat the app as offline-capable except for model/proxy calls** — GOALS.md already flags the Google Fonts VT323 CDN as breaking the offline/no-dependency promise; a downloadable app must bundle it. Transcripts and state stay local by default (privacy posture below). _(alt: Keep CDN font (breaks offline, leaks a request, fails in air-gapped use).)_

**Risks**

- Embedding any upstream provider key in the downloadable binary = immediate extraction and abuse; the credits-mode proxy MUST hold keys server-side and the app must only ever carry a revocable per-account token (CLAUDE.md already flagged this).
- Real metered cost is spikier and can be far higher than v7's friendly invented ranges (GPT 0.14-0.42/task). The $50/mo credit unit economics, objectives, and perks are tuned to fake numbers and need re-tuning against real spend, or a single heavy Opus/thinking session blows a month's credits in minutes.
- Runaway spend at high sim speed: the v7 loop can fan out many paid calls/second. Without decoupling game-time from real call cadence + a hard balance stop + a per-minute/-session spend cap, users (or a buggy loop) can burn real money uncontrollably.
- Money-transmitter / stored-value regulatory exposure: selling prepaid 'credits' redeemable for a service can trigger gift-card/stored-value rules depending on jurisdiction, rollover, and refundability. Keep credits non-refundable, non-cash, single-purpose, expiring; get legal review before scaling the credits tier. (BYOK launch sidesteps this entirely.)
- Real agents running shell/file/web on a user's machine is the dominant safety risk: prompt-injection in fetched web content or a deliverable could drive destructive shell/file actions. Object-gating + default-deny prompts + sandboxed workspace dir + domain allow-list are mandatory, not optional. The dev bypassPermissions setting must never ship.
- Truthful-telemetry is now a hard contract (GOALS principle 2): every number shown must trace to a real usage value. Streaming token deltas != final billed usage (cache/thinking/tool tokens) — must reconcile to the provider's final usage report or the meter is subtly wrong and erodes the core trust promise.
- Markup transparency / ToS: charging more than raw provider cost in credits-mode must be disclosed (it's a managed service, not pass-through). Some provider ToS restrict reselling/proxying API access — verify OpenRouter/Anthropic terms permit a metered reseller proxy before launching credits-mode.
- Transcript privacy: agent transcripts can contain user secrets, file contents, and PII. Default must be local-only with explicit opt-in before anything leaves the device; redact secrets from logs; clear ToS/privacy policy required before any cloud sync or telemetry.
- Top-up/refund abuse and chargebacks on Stripe; credit-balance accounting must be atomic server-side (decrement before/at dispatch) to prevent overspend races, especially with concurrent agents sharing one balance.
- Code-signing + auto-update is security-critical for a tool that executes code: an unsigned or hijackable update channel is a supply-chain attack vector. EV/OV cert + signed update manifests are required day one.

**Open questions**

- LAUNCH BILLING MODE: Confirm BYOK-first (fastest, zero key/billing/regulatory liability) vs going straight to managed credits (the real business, but blocked on proxy + Stripe + ledger + possible money-transmitter legal review). Recommendation is BYOK-first; do you accept delaying recurring revenue to ship faster and safer?
- MARGIN & PRICING: For the $50/mo Station Pass, does $50 grant exactly $50 of usage at COST (margin comes only from breakage/unused credits, Hermes-style) or $50 grants ~$38 of usage at a 25-30% markup (margin on every call)? These imply very different unit economics and different honesty framing in the in-game meter.
- CREDIT POLICY: Do monthly credits roll over or expire? Are top-ups refundable? (Expiring, non-refundable, single-purpose credits materially reduce stored-value/money-transmitter exposure — but hurt user goodwill.)
- ELECTRON vs TAURI: Port the vanilla-JS shell verbatim into Electron (fastest, larger/less-sandboxed binary) or rebuild the shell in Tauri (smaller, Rust core, better security posture for a tool that runs real shell/files)? This affects timeline, binary size, and the safety story.
- TOOL CAPABILITY SCOPE AT LAUNCH: Which real tools ship in v1 — model calls + image gen only (lowest risk), or also shell/filesystem/web (high value, high risk)? Object-gating supports a staged rollout (computer-only first, terminal/cabinet/uplink later).
- SANDBOX STRICTNESS: Confine agent shell/file ops to a per-agent workspace directory only (safest, but limits 'do real work on my computer'), or allow broader access behind per-action prompts (more powerful, more dangerous)? Where is the line for v1?
- WHO BEARS FAILED-CALL COST: In credits-mode, do users pay for calls that error/timeout/refuse (provider still bills tokens), or does the platform absorb retries? This affects both trust and margin.
- MAC/LINUX: Windows-only at launch (matches the user's environment and current vision) or cross-platform from day one? Affects signing/notarization and sandbox implementation effort.
- ORCHESTRATOR MODEL COST: The 'ULTRON' orchestrator that parses directives and configures agent purpose is itself a billed model call. Is orchestrator usage charged to the user's credits, bundled into the subscription base, or run on a cheaper fixed model to control cost?
