# PS-2026-077 — Gemini 3 thought-signature preservation

## Finding

The Alpha Overseer reached Gemini 3.8 Flash quickly, but its first multi-step tool turn failed with HTTP 400 after `brief_proceed`: Pine Star's Gemini stream parser extracted the native `functionCall` while discarding the sibling `thoughtSignature`. The provider-neutral loop then reconstructed the assistant tool call without that signed state, so the next GenerateContent request could not validate the current function-calling turn.

Gemini 2.5 Flash was not a viable fallback for this API user: the live API reported it unavailable to new users and directed use of Gemini 3.6 Flash. Gemini 3.8 Flash also rejected `MINIMAL`; Gemini 3.6 Flash is the current target and supports `MINIMAL`, `LOW`, `MEDIUM`, and `HIGH`.

## Change

- Carry exact Gemini `thoughtSignature` values as opaque, call-local provider metadata through the existing normalized tool-call seam.
- Restore that metadata only in the Gemini adapter, on the exact native `functionCall` part; preserve native function-call IDs through the paired `functionResponse`.
- Fail Gemini 3 responses before tool dispatch when the first function call in a model step lacks its required signature. Parallel sibling calls may remain unsigned as Gemini specifies.
- Strip opaque provider metadata on provider/model fallback and ignore foreign metadata at the Gemini wire boundary.
- Keep signatures out of assistant text, reasoning events, UI DTOs, and logs. Existing conversation/checkpoint persistence retains the exact normalized assistant tool call only where continuation/recovery requires it.
- Make the fallback Gemini model list target `gemini-3.6-flash`; keep its `MINIMAL` mapping and prevent the known 3.8 Flash `MINIMAL` combination at the existing capability/request seam.

The existing GenerateContent/REST provider remains in place. No API migration, approval bypass, tool authorization change, file-scope expansion, E-STOP change, or automatic tool approval was introduced.
