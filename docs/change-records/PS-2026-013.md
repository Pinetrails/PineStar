# PS-2026-013 — Auditor Objective Foundation

**Date:** 2026-08-27  
**Status:** Complete

## Intent

Make the Auditor system role useful through the existing durable objective and runtime lifecycle. Provide independent review work without introducing a second engine, auto-execution, or additional authority.

## Implementation

- Added an atomic `createAudit` store operation that accepts only a settled durable target.
- Requires a caller-supplied audit identity and makes same-target retries idempotent; reuse against a different target conflicts.
- Creates one objective declaring `audit` and `verify`, directly targeting the active `operations.auditor` role at the economy tier.
- Persists the audit-target relationship and a bounded request snapshot containing target status and evidence references.
- Gives the runtime directive only the target ID/title/status/role, bounded settlement summary, and evidence references. It explicitly asks for findings/exceptions without repeating or expanding the target action; no raw transcript is copied.
- Added authenticated `POST /api/objectives/audit` and escaped audit-target visibility in Reports. Admission, runtime identity, provider readiness, permission checks, cancellation, E-stop, and settlement remain unchanged.

## Safety

- Unsettled work cannot be represented as audited.
- Audit creation does not approve, admit, activate, publish, message, spend, install, access credentials, or grant tools.
- No external action or push occurred.
