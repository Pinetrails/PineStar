# PS-2026-074 — Alpha 1 desktop sidecar authentication bridge fix

## Finding

The Node sidecar was healthy and listening. The Tauri WebView initialization bridge rewrote root-relative `/api/*` requests to the private loopback port but omitted the sidecar's required per-launch `X-StarNet-Token`. Protected calls such as CloudSave `GET /api/save` therefore received 403 and correctly activated the SAVE-UNKNOWN safety gate.

## Change

- Extracted the central desktop fetch bridge into a testable initialization script.
- Route root-relative string API requests and same-app-origin `Request` API inputs to the launch's loopback sidecar.
- Merge the current launch token into `Headers` without discarding caller headers or fetch options.
- Leave all non-API, external, provider, and user-supplied destinations untouched and unauthenticated by this bridge.

The existing sidecar CORS allowlist already recognizes Tauri app origins and its preflight response narrowly permits `X-StarNet-Token`. No CORS, authentication middleware, CSP, save semantics, workspace, quarantine, or migration change was needed. The existing restart path retains the same port/token launch contract, so the WebView bridge does not become stale during a normal sidecar restart.
