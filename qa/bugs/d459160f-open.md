# `open()` has no `if (chanES) return` guard, so a re-entry (DATA › IMPORT → reentry → enterGame → resumeBridge) inside an SSE retry backoff leaves two live Event

## Symptom

After a sidecar restart followed by a DATA › IMPORT restore, one inbound channel message spawns two conveyor crates, HUD notes double up, and desk heat/prop pulses fire twice per event.

## Repro

1. With the app live, stop the sidecar so `chanES.onerror` fires repeatedly and `backoff` climbs toward 15s; wait until you are inside a pending retry (chanES is null — visible via `World.dbg().bridge.es === false`). 2. Restart the sidecar. 3. Within the backoff window open SETTINGS › DATA › IMPORT and restore a backup file (this runs reentry → enterGame → resumeBridge). 4. When the pending timer fires, two EventSources to /api/channels/events are open; send one Telegram/Discord message and watch two crates ride the belt and two '📡 message received' HUD lines appear.

## Evidence

`frontend/app/world.js:5994`

**Mechanism (read from the code):** `chanES.onerror` does `chanES = null; setTimeout(open, backoff)` with `backoff = Math.min(15000, backoff * 2)` (world.js:6004), and `open` itself only guards on `bridgePaused` — there is no `if (chanES) return;` (world.js:5994-5995). `resumeBridge()` re-opens on `!chanES` (world.js:5023) and is called from `enterGame` (app.js:2458). So if a retry is pending (chanES === null) when a second `enterGame` runs, `resumeBridge` creates EventSource #1 and the pending timer then creates #2; #1 is never closed and its `onmessage` closure `U.bus.emit(m.name, m.payload)` (world.js:6003) does not reference `chanES`, so it keeps re-emitting every server event onto the bus forever. Each additional re-entry inside a pending window adds another live stream. The reachable second-enterGame path is DATA › IMPORT: `fileImport.onchange` → `reentry()` (app.js:3897) → `resumeInto(saved)` → `enterGame`. Note the pause-based path does NOT exist: `disconnect()` (app.js:3666), the only caller of `World.pauseBridge()`, has zero call sites and is not on App's public API (app.js:3978).

**Existing test coverage:** none found — no test in test/ references resumeBridge, pauseBridge or connectChannelBridge. test/comms-link-honesty.test.js and test/app-boot-provider-truth.test.js only source-lock the `ls.bridged && !ls.paused && …` predicate shape.

**Adversarial verdict (survived refutation):** The mechanism is real, though it is the narrowest of the five. world.js:5994-5995 — `const open = () => { if (bridgePaused) return; ... chanES = new EventSource(...) }` — has no `if (chanES) return;`, and world.js:6004 `chanES.onerror = () => { try { chanES.close(); } catch (_) {} chanES = null; if (bridgePaused) return; setTimeout(open, backoff); backoff = Math.min(15000, backoff*2); }` leaves chanES null with a timer armed. resumeBridge (world.js:5018-5024) re-opens on `!chanES` and is called from enterGame (app.js:2458), so a re-entry inside the backoff window creates ES#1 and the pending timer then overwrites chanES with ES#2, orphaning ES#1 whose onmessage closure (`U.bus.emit(m.name, m.payload)`, world.js:6003) references no state that could stop it. connectChannelBridge is idempotent (`if (bridged ...) return;` world.js:5635-5637) so it is not the duplicate source — resumeBridge is. The reachable path checks out: app.js:3897 fileImport.onchange → reentry() (app.js:2187) → resumeInto → enterGame (app.js:2405), with no location.reload on that branch (the only reload, app.js:3831, is the cloud-save-unreachable gate). The claim's own caveat is also correct: disconnect() (app.js:3666) is the sole caller of World.pauseBridge and has zero call sites and is absent from App's returned API (app.js:3978-3987), so the pause-based variant is dead. No test references resumeBridge/pauseBridge/connectChannelBridge. Worth noting alongside it: the orphan's onerror closes the module-level `chanES` (now ES#2), not itself. P2 with low confidence is the honest rank — it needs an import performed inside a live backoff window.
